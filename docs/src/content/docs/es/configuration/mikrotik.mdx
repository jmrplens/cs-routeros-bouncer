Ajustes de la conexión a la [API de MikroTik RouterOS](https://help.mikrotik.com/docs/spaces/ROS/pages/47579160/API).

## Conexión

### `mikrotik.address` <Badge text="Obligatorio" variant="danger" />

<ConfigOption path="mikrotik.address" />

Dirección de la API de RouterOS en formato `host:port`. No tiene valor por defecto: el bouncer termina con `mikrotik.address is required` si el valor está vacío. El `192.168.0.1:8728` que se usa más abajo es el valor de ejemplo incluido en [`config/cs-routeros-bouncer.yaml`](https://github.com/jmrplens/cs-routeros-bouncer/blob/main/config/cs-routeros-bouncer.yaml), no un valor por defecto.

- Puerto `8728` — API en texto plano
- Puerto `8729` — API cifrada con TLS

```yaml
mikrotik:
  address: "192.168.0.1:8728"
```

### `mikrotik.username` <Badge text="Obligatorio" variant="danger" />

<ConfigOption path="mikrotik.username" />

El nombre de usuario de la API de RouterOS. No tiene valor por defecto: el bouncer termina con `mikrotik.username is required` si el valor está vacío. El nombre `crowdsec` es el valor de ejemplo incluido en [`config/cs-routeros-bouncer.yaml`](https://github.com/jmrplens/cs-routeros-bouncer/blob/main/config/cs-routeros-bouncer.yaml), no un valor por defecto. Usa un usuario dedicado con permisos mínimos. Consulta [Configuración del router](/cs-routeros-bouncer/es/getting-started/router-setup/) para crear el usuario.

### `mikrotik.password` <Badge text="Obligatorio" variant="danger" />

<ConfigOption path="mikrotik.password" />

La contraseña de la API de RouterOS.

:::tip[Variables de entorno]
Para valores sensibles como contraseñas, usa variables de entorno en lugar del archivo de configuración:

```bash
export MIKROTIK_PASS="your-secure-password"
```

:::

## TLS

### `mikrotik.tls` <Badge text="Opcional" variant="note" />

<ConfigOption path="mikrotik.tls" />

Habilita TLS para la conexión a la API de RouterOS. Requiere el servicio `api-ssl` en el router (puerto 8729).

```yaml
mikrotik:
  address: "192.168.0.1:8729"
  tls: true
```

### `mikrotik.tls_insecure` <Badge text="Opcional" variant="note" />

<ConfigOption path="mikrotik.tls_insecure" />

Omite la verificación del certificado TLS. Solo es necesario cuando el router usa un certificado autofirmado.

:::caution
Mantén `tls_insecure: false` siempre que sea posible: la configuración recomendada en producción es un certificado firmado por una CA en la que confíe el host del bouncer, de modo que la conexión quede cifrada y verificada. Establece `tls_insecure: true` solo para certificados autofirmados o para diagnósticos puntuales.
:::

## Tiempos de espera

### `mikrotik.connection_timeout` <Badge text="Opcional" variant="note" />

<ConfigOption path="mikrotik.connection_timeout" />

Tiempo máximo de espera para la conexión inicial a la API. Usa el formato de duración de Go.

### `mikrotik.command_timeout` <Badge text="Opcional" variant="note" />

<ConfigOption path="mikrotik.command_timeout" />

Tiempo máximo de espera para que se complete un único comando de la API. Auméntalo si tienes un router lento o address lists grandes.

:::tip
El límite es por comando, no por pasada de reconciliación, y el comando más lento no es un bloque masivo — esos tardan unos 130 ms cada uno. Es la lectura de la address-list al principio de cada pasada, que escala con cuántas entradas guarda el router. Medida en un RB5009 con 22.332 entradas, esa lectura tarda ~1,8 s, así que el valor por defecto de `30s` tiene unas 17× de margen y solo pasa a ser la restricción activa bastante por encima de las 350.000 entradas.

Súbelo si ves errores de tiempo de espera en un dispositivo lento o con una lista muy grande. Ambos tiempos de espera deben ser `>= 0`; `0` significa sin límite, y un valor negativo se rechaza al arrancar.
:::

## Pool de conexiones

### `mikrotik.pool_size` <Badge text="Opcional" variant="note" />

<ConfigOption path="mikrotik.pool_size" />

Número de sesiones de la API de RouterOS que el bouncer puede usar para el trabajo en paralelo, como las eliminaciones de la reconciliación. Un valor más alto aumenta el rendimiento cuando la reconciliación tiene que borrar muchas entradas obsoletas del address-list, y con `bulk_add_method: api` también cuando tiene muchas que añadir por un enlace con latencia; en la LAN del router una sola sesión añade más rápido, y cada sesión extra ocupa unos 1,7 MiB de RAM del router. Las decisiones en vivo siempre usan la conexión principal, así que no se ven afectadas.

- **Rango válido:** 1–20
- **Limitación automática:** al arrancar, el bouncer consulta el límite `max-sessions` del servicio API del router y reduce automáticamente el tamaño efectivo del pool para que nunca supere `max-sessions − 2` (reservando conexiones para el cliente principal y herramientas externas como WinBox).

```yaml
mikrotik:
  pool_size: 8 # Mayor paralelismo para las eliminaciones de la reconciliación
```

### Comprobar el límite del router

El servicio API de RouterOS tiene un ajuste `max-sessions` que limita las conexiones simultáneas. El valor de fábrica es **20**.

```routeros
# Comprobar el límite actual
/ip/service/print where name=api

# Aumentarlo (el valor máximo admitido es 1000)
/ip/service/set api max-sessions=1000
```

:::tip[Ajuste de rendimiento]
Para despliegues pequeños y medianos (≤ 5.000 IPs), el valor por defecto `pool_size: 4` es óptimo. Para listas de CAPI muy grandes (más de 20.000 IPs), aumentarlo a 6–8 puede reducir notablemente el tiempo de reconciliación. Verifica siempre primero el `max-sessions` del router:

```routeros
/ip/service/set api max-sessions=1000
```

:::

:::note
Cada conexión del pool es una sesión completa de la API de RouterOS. En routers con recursos limitados (p. ej., hAP lite), mantén `pool_size` bajo (1–2) para evitar presión de memoria.
:::

## Método de adición masiva

### `mikrotik.bulk_add_method` <Badge text="Opcional" variant="note" />

<ConfigOption path="mikrotik.bulk_add_method" />

Cómo añade la reconciliación (al arrancar y cada `crowdsec.reconciliation_interval`) las entradas del address-list que le faltan al router. Las decisiones en vivo no se ven afectadas: siempre se añaden con una llamada a la API cada una.

- **`script`** (por defecto): el bouncer envía hasta 100 adiciones como un único script de RouterOS. En RouterOS 7.8rc1 y posteriores es una sola llamada a `/execute` que ejecuta el script de forma síncrona: no se guarda nada en el router y nada llega a su log. En versiones anteriores, y para un bloque que `/execute` no puede ejecutar (por encima de su límite de 64 kB, o en un router que resulta no tenerlo), el bouncer crea un `/system/script` temporal, lo ejecuta y lo vuelve a eliminar. En ambos casos los viajes de ida y vuelta que cuesta un bloque no dependen de cuántas entradas tenga: uno mediante `/execute` y cuatro como script guardado. Por eso la latencia hasta el router pesa mucho menos que con `api`, que paga un viaje por entrada. Si un script falla, ese bloque se reintenta con una llamada por entrada.
- **`api`**: cada entrada se añade con su propia llamada a la API, y las llamadas se reparten entre las conexiones del pool (`pool_size`), o van una tras otra por la conexión principal cuando el pool no se pudo abrir. Nunca se crea un script, y la configuración del router no se toca.

En RouterOS anterior a 7.8rc1, RouterOS registra cada script guardado con su código completo al crearlo, una auditoría de `/system/script` muestra los scripts del bouncer apareciendo y desapareciendo, y cada alta y baja es un cambio de configuración que RouterOS guarda; `api` evita todo eso. A partir de 7.8rc1, `script` tampoco deja nada de eso, siempre que `/execute` ejecute el bloque; la vuelta al script guardado descrita arriba sí lo deja. `api` sigue sin ejecutar ningún script, y guarda en caché el id de cada entrada que añade, así que un unban en vivo justo después de una pasada de reconciliación elimina la entrada sin buscarla antes. Las entradas del address-list con timeout, que es en lo que se convierten las decisiones, son dinámicas y se quedan en memoria en ambos casos.

```yaml
mikrotik:
  bulk_add_method: api
  pool_size: 4 # las adiciones se reparten por el pool: ayuda con un enlace con latencia, no en la LAN del router
```

:::tip
Medido en un RB5009 (RouterOS 7.24.4), cargando unas 24.400 decisiones al arrancar:

- **En la LAN del router** (0,2 ms), `script` mediante `/execute` tardó unos 21 s y `api` con `pool_size: 1` unos 23 s, ambos con aproximadamente la mitad de CPU del router que un script guardado, que tardó unos 36 s. Con el `pool_size: 4` por defecto, `api` tardó lo mismo que un script guardado, porque aquí las sesiones extra solo compiten entre sí. Una pasada que añade unas pocas entradas tarda milisegundos con cualquiera de los dos.
- **Con un enlace con latencia**, cada adición por la API paga un viaje de ida y vuelta, mientras que un script paga uno por cada 100 entradas mediante `/execute` y cuatro como script guardado. A 36 ms, `script` tardó unos 33 s mediante `/execute`, 70 s como script guardado, y `api` 76 s con `pool_size: 16`; a 33 ms había tardado 3,7 min con 4 y 13 min con 1.

Las decisiones en vivo solo se procesan cuando ha terminado la primera reconciliación, y entre las pasadas siguientes.
:::
